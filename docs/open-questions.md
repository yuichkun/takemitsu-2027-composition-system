# 前提 — これが決まらないと設計できない

## Q1

### 手持ちのオーケストラ音源は何か

**演奏マップと再生方式の設計が、全面的にここに依存する。**

音源ライブラリごとに、キースイッチの流儀も、打楽器のマッピングも、
ダイナミクスを CC1 で扱うか CC11 か velocity かも違う。

**決める内容**

- 何を持っているか（弦・木管・金管・打楽器・ハープ・キーボードそれぞれ）
- 足りない楽器があるか。あるなら代替をどうするか
- 各音源のキースイッチ／CC の仕様

## Q2

### 曲そのものの構想がどれくらいあるか

**ここでシステムの性格が根本的に変わる。**

| 状態 | システムに求められること |
| --- | --- |
| 素材やイメージが既にある | その構想を実現する形に特化できる。素材の入口が限定される |
| 白紙から立ち上げる | 発想を誘発する機能が要る。素材の入口を広く持つ必要がある |

**決める内容**

- 既にある素材・着想は何か
- 編成・長さ・性格について、既に決めていることがあるか

# 工学の論点

## Q3

### VST ホスティングの方式

選択肢は [`proposal.md` 4.4節](./proposal.md#44-vst-ホスティング--選択肢)に列挙してある。
大きくは「既存 DAW を借りる（Reaper 等）」「自前で書く（JUCE ヘッドレス等）」
「既存ヘッドレスホストを使う（Carla 等）」「VST を使わない」「二段構え」。

**決める内容**

- どの方式を採るか
- Reaper を採る場合、ライセンスを持っているか
- 即時プレビュー用の軽量経路を併設するか

**僕の見立て:** 二段構え（軽量な即時プレビュー + 高品質オフラインレンダ）が、
判断の種類ごとに必要な忠実度が違うという性質と噛み合う。
高品質側は Reaper と JUCE ヘッドレスのどちらも現実的で、
**JUCE の資産と経験が既にあるなら自前ホストの制御性は魅力的**だと思う。

## Q4

### アプリケーションの形態

選択肢は [`proposal.md` 4.3節](./proposal.md#43-アプリケーションの形態--選択肢)。

Web ベースであることは合意している。決まっていないのは外側の器。

**決める内容**

- ブラウザのまま行くか、Electron / Tauri に包むか
- 包む場合、それを最初から行うか、後から移行するか

**僕の見立て:** Electron はメインプロセスから VST ホストを直接叩けるので、
Q3 の選択と連動する。自前ホストを N-API アドオンにするなら Electron が効いてくる。
外部プロセスに委ねるなら、器はいつ被せても同じ。

## Q5

### 譜面プレビューの実装

選択肢は [`proposal.md` 4.5節](./proposal.md#45-譜面プレビュー--選択肢)。

**決める内容**

- Verovio / OSMD / VexFlow / MuseScore CLI / 自前描画のどれを採るか
- 複数を併用するか（Sibelius とは別実装による第二の検証として）

**僕の見立て:** Sibelius に渡すのと同じ MusicXML をプレビューにも食わせると、
プレビューが輸出の検証を兼ねる。この性質は強い。
ただし Verovio の描画は Sibelius の描画ではないので、
「内容の検証」にはなっても「見た目の保証」にはならない。

# 感性の論点

## Q8

### 奏法の語彙をどう決めるか

**技術的都合と作曲上の決定が一致する場所。**

演奏マップの整備量は `使用楽器数 × 使用奏法数` に比例する。
同時に、限定された語彙を明確な意図で使い分けることは、
審査員が繰り返し批判している「一様に高密度で匿名的なスコア」の正反対にある
（[`research/takemitsu-award-2027.md`](./research/takemitsu-award-2027.md)）。

**決める内容**

- この曲で使う奏法を何にするか
- どこまで絞るか。絞らない選択もありうる

**僕の見立て:** これを「妥協」ではなく**作曲上の第一決定**として先に置きたい。
ただし何を選ぶかは完全に余湖さんの領域。

## Q9

### 編成をどう決めるか

規定の上限内で、実際に何を使うか。

**決める内容**

- 使う楽器と人数
- 打楽器4奏者に何を割り当てるか（持ち替えの物理的成立を含む）
- キーボード2奏者を使うか。使うならシンセを含めるか
- 「その他の管楽器1」の枠を使うか

**僕の見立て:** 上限いっぱいを使う必要はまったくない。
ターネジが名指しで批判しているのは、むしろ大編成を常時鳴らす書き方。

## Q10

### 演奏時間をどこに置くか

規定は10分以上20分未満。

| 選択 | 効いてくること |
| --- | --- |
| 短め（10〜13分） | 書く量と浄書量が減る。形式を凝縮できる。ドラマの振幅を取りにくい |
| 中程度（13〜17分） | 境界から遠く安全。標準的 |
| 長め（17〜19分台） | 大きな時間設計ができる。境界に近く、テンポ解釈で下限・上限を割るリスク |

**決める内容:** どこを狙うか。

**僕の見立て:** 境界に近づけるほど、テンポの解釈で規定を外すリスクが上がる。
ただしこれは危険度の話であって、音楽的にどうしたいかが先に来るべき。

## Q11

### 形式（ドラマの曲線）をどう表現するか

[規律3](./proposal.md#規律3--形式は手で引く)により、形式は生成の前に人間が引く。
その「引く」対象を、システム上でどう表現するか。

**決める内容**

- 時間設計を何で持つか（区間の列か、連続曲線か、注釈つきタイムラインか）
- 密度・レジスター・緊張度などの軸を何本持つか
- 引いた曲線が生成をどう拘束するか（強制か、参照値か）

**僕の見立て:** ここは実際に使ってみないと形が決まらない類の設計だと思う。
最初は素朴な形で置いて、作曲しながら育てるのが現実的。
