## 決着している前提

- **応募資格（年齢）を満たしている。** 2027年度への応募が成立する
- **四分音までを使う音楽にする。** スペクトル解析的なアプローチと、
  限定された音程を組み合わせで数学的に探求するアプローチを想定
- **恣意的なメロディを入力するケースは少ない。**
  素材は解析と数学的構成から来るのであって、即興の採譜からは来ない
- 手法の系譜は、**リゲティ／クセナキスのアルゴリズミックな手法、あるいはミュライユ／グリゼーの
  スペクトル手法**。余湖さんは Opusmodus での作曲経験を持つ
- **データの最小単位は音符ではなく、より上位の単位にする**
  （[`decisions/0005`](./decisions/0005-gesture-as-primitive.md)）。
  「ジェスチャー」という概念と名前は、設計の中で別の概念に置き換えてよい
- オーケストラ音源は **BBC Symphony Orchestra Professional**。足りない音は余湖さんがサンプルを探して足す
  （[`decisions/0012`](./decisions/0012-bbcso-with-user-samples.md)）
- **四分音より細かい音高は使わない。** 四分音は調律を変えた音源インスタンスで鳴らす
  （[`decisions/0013`](./decisions/0013-quarter-tones-by-instance-tuning.md)）
- 作曲層と、鳴らす・見せる土台は **楽譜の JSON** で分ける。強弱は連続値で持ち、記号への丸めは記譜の側で行う
  （[`decisions/0014`](./decisions/0014-score-json-contract.md)）
- **ディヴィジは記譜と再生の両方で扱う**（[`decisions/0015`](./decisions/0015-divisi-first-class.md)）
- プレビューは **vp dev のブラウザ画面**、譜面は Verovio（[`decisions/0016`](./decisions/0016-preview-in-browser.md)）
- **即時プレビューは不要。** 高品質オフラインレンダのみでよい
- **規定リンターは作らない。** 提出前に人間と AI で一度点検する
  （[`decisions/0009`](./decisions/0009-no-linter.md)）

# 工学の論点

## Q12

### 四分音を MusicXML でどう表現し、Sibelius にどう渡すか

**四分音を使うと決まった時点で、これが最大の技術的リスクになった。**
記譜と再生の両側で、通常の半音階を前提とした経路が壊れる。

**記譜側も再生側も、四分音そのものは決着した。**

- 記譜: MusicXML の `<alter>` に小数値を書けば Sibelius 標準の四分音記号が付く
  （[`decisions/0011`](./decisions/0011-quarter-tone-notation.md)、
  実測は [`research/sibelius-musicxml-import.md`](./research/sibelius-musicxml-import.md) 2.5節）
- 再生: 調律を +50 セントにした音源インスタンスで鳴らす
  （[`decisions/0013`](./decisions/0013-quarter-tones-by-instance-tuning.md)）

**残っている内容**

- 移調楽器・小節内の臨時記号規則・持ち替えとの組み合わせ。第1回テストの手作りフィクスチャは片付けた。
  記譜の射影が出す MusicXML で取り込みを確かめ直す
- 取り込みで落ちる記譜（ハーモニクスの○、Bartók pizz.、+、niente、延長破線、奏法遷移の線、
  トリルの補助記号、波線、持ち替え）をどう補うか。ManuScript プラグインで置く案は動作確認が取れていないので一度消した。
  必要になったら作り直す

## Q5

### 譜面プレビューで四分音・奏法・打楽器が描けるか

描画は Verovio に決まった（[`decisions/0016`](./decisions/0016-preview-in-browser.md)）。
Sibelius に渡すのと同じ MusicXML を描く。

**確かめる内容**

- 小数の `<alter>` から四分音の臨時記号を描くか。描かないなら `<accidental>` を併記する
- 奏法テキスト、ヘアピン、打楽器の譜表と符頭、ディヴィジの譜表がどこまで出るか

## Q6

### 作曲層の言語と表現

土台との境界は楽譜の JSON に決まった（[`decisions/0014`](./decisions/0014-score-json-contract.md)）。
土台は TypeScript で書き、音高は四分音の格子に限る。作曲層は JSON を書き出せれば何でもよい。

**決める内容**

- 作曲コードを書く言語
- ジェスチャーの表現形式（型で持つか、データで持つか、DSL を作るか）

**僕の見立て:** 余湖さんが Opusmodus の経験を持つことが参照点になる。
Opusmodus の OMN 表記は音価・音高・強弱・奏法を1つの列の中に並べて書く形式で、
音符より上位の単位（[`decisions/0005`](./decisions/0005-gesture-as-primitive.md)）を
テキストとして読み書きする実例になっている。
**作曲コードの読み心地を OMN に寄せるか、別の形を採るか**も、ここで決める内容に含める。

# 感性の論点

## Q13

### 個人の声をどこに宿すか

**素材が解析と数学的構成から来るなら、[規律1（素材の出自）](./proposal.md#規律1--素材の出自を記録する)
の前提が変わる。** 出自は「どの即興か」ではなく「どの解析・どの構成・どのパラメータか」になる。

そして審査員が繰り返し指摘している落選の典型
（[`research/takemitsu-award-2027.md`](./research/takemitsu-award-2027.md)）と、
正面から向き合う必要がある。

**両方の読みが成り立つ**

| 読み | 内容 |
| --- | --- |
| **危険側** | スペクトル的・微分音・テクスチュア主体は、ヴィトマンが「複雑で微細に区別されたテクスチュア」と呼んで、その背後に個人の声が聞こえないと言った当のもの。この20年で最も一般化した現代音楽の語法でもある |
| **有利側** | 「**限定された**音程を組み合わせで数学的に探求する」は、密度の高いテクスチュアとは逆。素材を絞って徹底的に扱うのは、近藤譲が評価し、ターネジが「明瞭さ」と呼んだものに近い |

**決める内容**

- 声をどこに宿すか。素材か、形式か、選択の仕方か
- 何を「自分でなければこうしない」判断として意識的に置くか

**僕の見立て:** 素材が数学的に導かれるなら、**声は「何を選ばなかったか」と
「どう時間に配置したか」に宿る**ことになる。つまり形式と選択。
これは [規律3（形式は手で引く）](./proposal.md#規律3--形式は手で引く)の重要度を上げる。

余湖さんが antara の方針として示した音程のセリー（[`antara/interval-series.md`](./antara/interval-series.md)）は、
この論点への一つの答えの形をしていると思う。声は、どの音程をどれだけ使うかの選び方と、
調性への立ち位置（避けも戻りもせず、結果として生じさせる）に宿る。

## Q8

### 奏法の語彙をどう決めるか

演奏マップの整備量は `使用楽器数 × 使用奏法数` に比例する。
同時に、限定された語彙を明確な意図で使い分けることは、
審査員が批判している「一様に高密度で匿名的なスコア」の正反対にある。

**決める内容**

- この曲で使う奏法を何にするか
- どこまで絞るか。絞らない選択もありうる

BBC SO にある奏法とない奏法（[`research/bbcso.md`](./research/bbcso.md)）と相互に効く。
ない奏法はサンプルで足せる（[`decisions/0012`](./decisions/0012-bbcso-with-user-samples.md)）。

## Q9

### 編成をどう決めるか

規定の上限内で、実際に何を使うか。

**決める内容**

- 使う楽器と人数
- 打楽器4奏者に何を割り当てるか（持ち替えの物理的成立を含む）
- キーボード2奏者を使うか
- 「その他の管楽器1」の枠を使うか

**僕の見立て:** 上限いっぱいを使う必要はまったくない。
ターネジが名指しで批判しているのは、むしろ大編成を常時鳴らす書き方。

## Q10

### 演奏時間をどこに置くか

規定は10分以上20分未満。

| 選択 | 効いてくること |
| --- | --- |
| 短め（10〜13分） | 形式を凝縮できる。ドラマの振幅を取りにくい |
| 中程度（13〜17分） | 境界から遠く安全 |
| 長め（17〜19分台） | 大きな時間設計ができる。境界に近く、テンポ解釈で上限を割るリスク |

## Q11

### 形式（ドラマの曲線）をどう表現するか

[Q13](#q13) により、**この論点の重要度が上がった。**
素材が数学的に導かれるなら、作曲者の判断が最も濃く現れるのは形式の側になる。

**決める内容**

- 時間設計を何で持つか（区間の列か、連続曲線か、注釈つきタイムラインか）
- 密度・レジスター・緊張度などの軸を何本持つか
- 引いた曲線が生成をどう拘束するか（強制か、参照値か）

# antara の論点

曲の方針は [`antara/interval-series.md`](./antara/interval-series.md)。
音程の値（どの音程をどれだけ）は、曲の流れ次第で決める（余湖さん）。ここに置くのは、書き方そのものの論点。

## Q14

### 音程の組の中をどう並べるか

Quantization は「順列」と呼んでいたが、コードは組合せで、各組の中を小さい順に並べていた。
そのため全部の断片が、沈んでから大股に駆け上がる同じ形をしていた。

| 選択 | 効いてくること |
| --- | --- |
| 組合せと、並べ方の規則 | 形が身振りとして揃う。規則そのもの（小さい順、大きい順、交互…）が選べる |
| 順列 | 並べ方も全部回す。形が毎回変わる。組の数が桁違いに増える |
| 並べ方も差の列として決める | 上がる・下がるの順を、別の列として持つ |

**僕の見立て:** 組合せと並べ方の規則を既定にして、規則をつまみにする。形が揃っていると、耳が色の違いのほうへ向くと思う。聴いて確かめる。

## Q15

### リズムで「結果として生じる」ものは何か

| 選択 | 差 | 結果として生じるもの |
| --- | --- | --- |
| 時間の差 | 鳴り始めの間隔（16 分が 2、3…） | 拍子（小節の頭がどこか） |
| 長さの比 | 前の長さとの比（2:1、3:2…） | 拍の速さ |
| 音程をそのまま比に写す | 音程を振動数の比として読み、時間の比にする（5 度 = 3:2） | 音と時間が同じ集合から決まる |

**僕の見立て:** 時間の差から始める。起点から差を足す、色と場所、1 周の合計で固まるかどうか、が音程とそのまま対応し、譜面にも書ける。
残りの 2 つは、それを聴いてから重ねるかを決める。

## Q16

### 四分音を音程のセリーにどう入れるか

四分音までを使うことは、このプロジェクトの最初からの与件。

| 選択 | 効いてくること |
| --- | --- |
| 入れない | 音程の集合は半音の格子。調性感が結果として生じるかを、耳が一番知っている格子で聴ける |
| 集合の中の音程として入れる（3.5 など） | 踏むたびに、+50 セントずれたもう一方の 12 音へ渡る |
| 二つの 12 音を並べる | 同じ差の歩きを、+50 セントずらしてもう一つ走らせる |

**僕の見立て:** まず半音の格子で「結果として生じる」を聴けるようにし、四分音は曲の決まった場所で向こう側へ渡る出来事として置く。
ただ、余湖さんの意図を先に聞きたい。

## Q17

### 同じ構図をどこまで広げるか

音高とリズムのほかに、形式（起点の動き。Quantization では段ごとに 5 度上へ）、強弱、音域、配器、密度に同じ構図を使えるか。

**僕の見立て:** 音高、リズム、形式の 3 つ。強弱と配器は、この 3 つを聴いてから決める。
