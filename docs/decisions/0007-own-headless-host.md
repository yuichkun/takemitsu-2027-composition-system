# 0007. VST ホストは自作のヘッドレス CLI にする

- 状態: 採用
- 関係する論点: Q1 / Q12

## 背景

オフラインレンダリング（[0004](./0004-offline-render.md)）を行うには、
VST3 のオーケストラ音源をホストする何かが要る。Chromium の中に VST3 はロードできないため、
ここだけは必ずネイティブのプロセスになる。

制約が2つある。

- **余湖さんの持ち物や知見を前提にした案は採れない。** Reaper は所持しておらず、JUCE の知見もない。
  コードを書くのは Claude であり、**作業や学習コストを余湖さんに押し付ける構成は不可**
- **四分音を扱う**（[0008](./0008-quarter-tone-native.md)）。
  ノートごとのピッチベンドと MIDI チャンネル割り当てを厳密に制御する必要が生じうる

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. Reaper + ReaScript | 既存 DAW をレンダリングエンジンとして借りる | スクリプト性は高い。**購入が必要で、テンプレートプロジェクトの構築という GUI 作業が余湖さんに発生する。**制約に反する |
| B. Carla（ヘッドレス + Python API） | 既存のプラグインホストを使う | 実装量が減る。外部依存が増え、微分音のための細かい MIDI 制御を差し込みにくい |
| C. pedalboard（Python） | VST3 をロードして MIDI からレンダリングできる | 最も早く動く。**pip でのインストールは余湖さんが禁じている**ため、導入の可否から相談が要る |
| D. 自作ヘッドレス VST3 ホスト（C++ / JUCE） | プラグインをロードし、プラグイン状態を適用し、MIDI を流して WAV を書き出す CLI | 完全な制御。ピッチベンドとチャンネル割り当てを厳密に扱える。楽器ごとのステム出力が自然。**Claude が書き、余湖さんは実行するだけ**。実装量は最も多い |
| E. 自作ホスト（Rust） | 同上を Rust で | 言語の統一。VST3 ホスティングの資産が C++ に比べ薄い |

## 決定

D を採る。**ヘッドレスの VST3 ホスト CLI を C++ / JUCE で自作する。**

役割:

- プラグインをロードし、保存されたプラグイン状態を適用する
- MIDI（ピッチベンドとチャンネル割り当てを含む）を流す
- 指定範囲をオフラインでレンダリングし、WAV を書き出す
- 楽器ごとのステムを個別に出力できる

## 理由

- **購入も学習も余湖さんに要求しない。** 制約を満たすのはこの案と E だけ
- **四分音のためのピッチベンドとチャンネル管理を、こちらが完全に制御できる。**
  既存 DAW や既存ホストに載せると、この層に手が届かないか、回り道が要る
- どの音源を選んでも動く。[Q1](../open-questions.md#q1) の結論に依存しない
- 決定論的なオフラインレンダになる。同じ入力から必ず同じ音が出る

## 結果と副作用

- **実装量が最も多い案を選んだ。** ここは Claude が引き受ける
- **プラグイン状態の初期設定に GUI 操作が一度だけ必要になる。**
  Kontakt 等に楽器をロードする作業は GUI でしか行えないため、
  ホストに「エディタを開いて状態を保存する」モードを用意し、楽器ごとに一度だけ行う
- C++ のビルド環境が要る
- 音源が物理モデリング系（プラグイン1つ＝楽器1つ、状態設定が軽い）になれば、
  上記の初期設定の手間はほぼ消える。[Q1](../open-questions.md#q1) と連動する
