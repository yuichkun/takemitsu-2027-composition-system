# 0006. 記譜の輸出可能性を、実装より先に実機で検証する

- 状態: 提案
- 関係する論点: R1 / R2

## 背景

システムが出力すべき MusicXML の内容は、**Sibelius が何を取り込めるかによって決まる**。

MusicXML の仕様に存在する要素が、実際の Sibelius の取り込みで生き残るとは限らない。
とくに打楽器（`unpitched` + 表示位置 + 楽器参照）は表現が複雑で、
取り込みが崩れやすい領域として知られている。

強弱・奏法・エクスプレッションが落ちると、[0005](./0005-gesture-as-primitive.md) が
満たそうとしている要求そのものが成立しなくなる。

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. 実装してから確かめる | システムを作り、出力を Sibelius に入れてみる | 早く動き出す。**欠落が判明したとき、射影の設計をやり直すことになる** |
| B. 先に実機で検証する | 使いそうな記譜要素を詰めたテストファイルを手で作り、Sibelius に読ませる | 何を出力すべきかが確定してから設計できる。着手が遅れる |

## 決定

B を提案する。**コードを書く前に、実機の Sibelius で確認する。**

検証対象に含めるもの:

- 強弱記号、ヘアピン、`cresc.` / `dim.` の楽語
- テンポ変化、テンポの文字指示
- アーティキュレーション（各種）
- 奏法テキスト（`sul pont.`、`col legno`、`pizz.`、ハーモニクス、ミュート等）
- 弦のディヴィジ表記
- 連符、装飾音
- **打楽器**（複数楽器の譜表、符頭の指定、ティンパニ、持ち替え）
- ハープ、キーボード
- 拍子の変化

あわせて次も確認する。

- **VST レンダ経路**: 手持ちの音源1つで、MIDI + キースイッチから WAV が出るまでを通す
- **Sibelius プラグイン（ManuScript）の要否**: 取り込み後に大量の手作業が発生する項目が
  判明した場合にのみ、その自動化を検討する。**判断はテスト結果を見てから行う**

## 理由

- **Sibelius に何が渡るかが、システムが何を出力すべきかを決める。** 逆順にやると作ったものを捨てる
- 打楽器は最も崩れやすく、かつ規定で4奏者に制限されているため、
  記譜と物理的成立の両面で早期の確認が要る
- 欠落の発見が遅れるほど手戻りが大きくなる、という性質を持つ領域

## 結果と副作用

- コードを書き始めるまでに、実機での作業が入る。この作業は Sibelius を持つ人間にしかできない
- テスト結果が、MusicXML 射影の実装範囲を規定する。
  生き残らないと分かった要素は、別の手段（ManuScript プラグイン、浄書時の手作業）に回す
- 検証結果は調査ノート（R1 / R2）として残し、実装の根拠にする
