# 0002. 作品の正本をコードにする

- 状態: 採用
- 関係する論点: Q6

## 背景

このプロジェクトは「AI との協業によるメタプログラミング」を柱のひとつに据えている
（[`../proposal.md` 2章](../proposal.md#2-作曲行為の定義)）。
その前提として、**AI が作品を編集できる形式であること**が要る。

作曲環境の正本の置き方には根本的な分岐がある。GUI で編集した内部状態を正本にするか、
人間と AI の両方が読み書きできるコードを正本にするか。

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. GUI の内部状態が正本 | 一般的な作曲ソフトの形 | 直接操作できる。AI は「操作の代行」しかできず、編集主体になれない。diff が読めない |
| B. コードが正本、GUI は計器 | コードを書くと譜面と音になる | AI が対等な編集者として入れる。diff が意味を持つ。git がそのままバージョン管理になる。直接操作の即物性は落ちる |
| C. 両方を正本にして同期 | 双方向 | どちらの利点も得られる。同期の一貫性を保つコストが常時かかり、破綻しやすい |

## 決定

B を採る。**作品の実体は、人間と AI の両方が読み書きできるコード。**
GUI（譜面プレビュー、ピアノロール、各種可視化）は、そのコードの状態を見るための計器として上に載る。

## 理由

- **AI が編集主体になれることが、柱4の存在条件そのもの。**
  GUI 状態が正本だと、AI は操作を代行するだけの存在に落ちる
- diff が意味を持つ。何をどう変えたかが読め、レビューできる
- git がそのまま音楽のバージョン管理になる。
  **捨てた案が失われないことが、大胆な試行を可能にする**
  （[`../proposal.md` 6.4節](../proposal.md#64-驚きをどう設計するか)）
- 同期を持たないので、C の破綻リスクを負わない

## 結果と副作用

- 音符を直接いじる即物性が下がる。GUI からの編集を入れたくなったときは、
  「GUI がコードを書き換える」形にする必要がある
- コードの読みやすさが、そのまま作曲のしやすさになる。表現形式の設計が重要になる（Q6）
- 譜面プレビューは常に「コードの結果」であって、編集面ではない
