# 0014. 作曲層と、鳴らす・見せる土台を、JSON の楽譜で分ける

- 状態: 採用
- 関係する論点: Q6 / Q4

## 背景

鳴らす仕組み（BBC SO での再生）と見せる仕組み（譜面プレビュー、Sibelius への MusicXML）を、
作曲の方法に依存しない汎用の土台として作る。作曲層は**完全に別のもの**として、あとから何が来てもよいようにする
（余湖さん、2026-09-27）。

作曲層と土台の境界の形を決める必要があった。

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. JSON ファイル | 作曲層は楽譜を JSON で書き出す。土台はファイルを読む | 作曲層の言語を問わない。境界が目で読める |
| B. TS モジュール | 作曲コードが楽譜のオブジェクトを返す関数を export する | 型がそのまま効く。作曲層が TS に縛られる |

## 決定

A を採る。**作曲層は「楽譜の JSON」を書き出し、土台はそれだけを入力にする。**
TS の型と検証を土台の側に置く（[`../../src/score/`](../../src/score/)）。

楽譜の JSON が持つもの:

- パート（楽器の参照、奏者数）、拍子と小節、テンポ
- 音符: 位置と長さ（四分音符単位の有理数）、音高（四分音まで）、声部、譜表
- 強弱: **連続値**。作曲層は細かい解像度で持ち、pp や mf のような記号への丸めは記譜の射影が行う
- 奏法、アーティキュレーション、打楽器の楽器と奏法、テキスト

作曲層の語彙（素材、ジェスチャー、配器）は入れない。
それらは作曲層の中で扱い、最終的に楽譜の JSON へ具体化する。

## 理由

- 作曲層を完全に分けるには、言語を問わない境界がいちばん強い
- 余湖さんも JSON がよいと判断した
- 強弱を連続値で持つのは余湖さんの指摘による。作曲の判断は記号より細かい解像度で行われ、
  記号は記譜の都合で決まる。粗い記号を正にすると、作曲層の情報が落ちる

## 結果と副作用

- 作曲層がどの言語で書かれても、プレビューと再生はそのまま使える
- 強弱から記号とヘアピンを導く規則を、記譜の射影が持つことになる。導き方が譜面の読みやすさを左右する
- [0005](./0005-gesture-as-primitive.md) のジェスチャーは作曲層の概念として残り、土台には現れない
