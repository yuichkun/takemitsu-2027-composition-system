# 0003. Sibelius は浄書専用とし、MusicXML は片道の出口にする

- 状態: 採用
- 関係する論点: なし

## 背景

最終成果物は製本された紙のスコアであり、浄書は Sibelius で行う。
このとき、Sibelius をどう位置づけるかで設計が大きく変わる。

作曲行為の一部を Sibelius でも行うなら、Sibelius 側の変更を作曲システムに戻す経路が要る。
MusicXML の**往復**を成立させるのは、記譜情報の欠落とレイアウト情報の扱いのために難しく、
実装コストが桁で変わる。

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. 往復同期 | Sibelius 側の編集をシステムに戻す | どちらでも作曲できる。MusicXML の往復忠実性という難問を抱え込む |
| B. 片道 | システム → Sibelius の一方向。Sibelius では浄書のみ | 実装が大幅に単純になる。Sibelius で行った変更は正本に戻らない |

## 決定

B を採る。**Sibelius では作曲行為を一切行わない。** 浄書（レイアウト、間隔、譜めくり、
見た目の調整）のみを行う。MusicXML はシステムからの片道の出口とする。

## 理由

- 作曲は作曲システム側で完結するという前提が既に置かれている。往復の必要がない
- MusicXML を内部表現にする必要がなくなる。
  内部表現は柱3・柱4に都合のいい形（コードとして扱いやすい形）を自由に選べる
- 往復忠実性という、このプロジェクトの目的に何も寄与しない難問を回避できる

## 結果と副作用

- **Sibelius で行った変更は正本に反映されない。**
  したがって浄書段階で音楽的な変更が必要になったら、システム側で直して出し直す規律が要る。
  これを破ると正本と成果物が乖離する
- MusicXML に載らない情報は Sibelius に渡らない。
  何が載るかを実機で確認する必要がある（[0006](./0006-verify-before-build.md)）
- 浄書のやり直しコストが発生するので、**引き渡しを最後に一度だけ行うのではなく、
  早期から繰り返す**ことが重要になる
