# 0001. ドキュメントを4種別に分けて運用する

- 状態: 採用
- 関係する論点: なし

## 背景

プロジェクトの初期に、ドキュメントの運用ルールを決め切っておきたかった。

放っておくと2種類の文書が混ざる。ひとつは「今どうなっているか」を書いた文書で、
常に最新でなければ意味がない。もうひとつは「いつ何をやったか」の記録で、
過去のまま残らなければ意味がない。

この2つを1つのファイルに混ぜると、どちらの役目も果たせなくなる。
仕様書に経緯が積もって読めなくなり、記録が書き換えられて信用できなくなる。

このプロジェクトは、賞の規定という**外部から与えられた動かせない事実**と、
**まだ何も決まっていない設計**と、**調べて分かったこと**が同時に存在する状態から始まる。
混ぜると、規定なのか提案なのか調査結果なのかが読み手に区別できなくなる。

## 選択肢

| 案 | 中身 |
| --- | --- |
| A. 1種類にまとめる | 管理は楽。更新の仕方が定まらず、上の問題が起きる |
| B. 仕様とログの2種別 | 素直。「なぜそう決めたか」と「調べた結果」の置き場が定まらない |
| C. 4種別に分ける | 役割がはっきりする。ファイルが増え、振り分けの判断が要る |

## 決定

C を採る。`~/workspace/mirai-no-tamago` で運用実績のある方式をそのまま踏襲する。

| 種別 | 場所 | 更新の仕方 |
| --- | --- | --- |
| 仕様 | `docs/*.md` | 今の正解だけを書く。変わったら書き換える |
| 決定記録 | `docs/decisions/` | 1決定1ファイル。書いたら変えない |
| 調査ノート | `docs/research/` | トピック単位。出典と確度を明示。更新してよい |
| 作業ログ | `docs/worklog/` | 日付順に追記。過去を書き換えない |

あわせて、仕様には**時制や変化を表す表現を使わない**ことにする。

## 理由

- 決定記録を分けたことで、**仕様から経緯を追い出せる**。仕様が短く保たれる
- 調査ノートを分けたことで、事実と設計判断を混ぜずに済む。
  出典と確度を明示する規律も、そこにだけ課せばよくなる
- 作業ログを追記専用にしたことで、**失敗の記録が消えない**
- 既に運用実績のある方式なので、運用ルール自体を発明する必要がない

## 結果と副作用

- 「これはどこに書くのか」という判断が毎回発生する。
  振り分けの基準を `docs/README.md` に表と図で置いて軽くする
- 同じ事実が複数の場所に現れうる。正本は1箇所に置き、他からはリンクする
- ファイルが増える。**中身のない器を先に作らず、書くことができてから作る**
