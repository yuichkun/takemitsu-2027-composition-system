# 0018. レンダは小節ごとのチャンクで、常駐ホストに丸ごと頼む

- 状態: 採用
- 関係する論点: 15〜20 分の曲を書きながら、直してすぐ聴けること

## 背景

レーン（パート × 調律）を通しで 1 本ずつレンダし、レーンの中身のハッシュでキャッシュしていた。20 分・107 パートのダミー曲
（`tools/stress-score.ts`）で測ると、1 パート直すたびにそのパートを 20 分ぶん作り直し、全体のミックスにはメモリが約 49 GB 要った。
譜面は 65 MB の MusicXML を Verovio が 187 秒かけて読み、落ちた。

余湖さんの方針: 速さが一番。ただしバグを入れにくい単純な作りにする。常駐はよいが、差分を送る作りは避ける。

## 選択肢

| 案 | 中身 | 効いてくること |
| --- | --- | --- |
| A. 30 秒ごとの区間 | 時間で切り、前の区間を少し重ねて鳴らしてつなぐ | 途中に 1 小節足すと、後ろの区切りが全部ずれて作り直し。重ねてつなぐ所にずれの余地 |
| B. 小節ごとのチャンク | 音符を鳴り始めの小節に丸ごと入れ、余韻ごと書き出して足す | 小節を足しても後ろは作り直さない。切り貼りがない |
| C. 常駐ホストに差分を送る | ホストが楽譜を覚え、足した音符・消した音符だけ送る | 速いが、ホストの覚えている楽譜と本物がずれうる |
| D. 常駐ホストに丸ごと送る | ホストは音源だけ持ち、毎回「この音色で、この音符を」を送る | ずれようがない。送る量は増えるが、ローカルなので問題にならない |

## 決定

B と D を採る。チャンクのキーは、ホストへの依頼そのもののハッシュにする。

- 再生は、パートごとの 2 秒のセグメントをサーバがチャンクから混ぜて、ブラウザが少し先まで取り寄せる
- 譜面は数小節ずつの MusicXML（窓）に分け、見えている所だけ描く。窓も中身のハッシュで覚える
- 通しでレンダする遅い経路は答えとして残し、`tools/check.ts` で速い経路と比べる

## 理由

- 送る中身とキーが同じものなので、キーに入れ忘れた条件で古い音が残る、ということが起きない
- 「どこが変わったか」を追う処理がない。楽譜は毎回まるごと計画し直し、キーで引くだけ
- 常駐ホストが落ちても、同じ依頼を送り直すだけで済む

## 結果と副作用

- 使い回したインスタンスでは短い音のラウンドロビンが変わる。音量の推移は平均 2 dB 以内。答え合わせは波形でなく音量で比べる
- 1 つの楽器で新しい奏法を使うと、その楽器のチャンクは全部作り直しになる（楽器ごとに読み込む奏法をまとめているため）
